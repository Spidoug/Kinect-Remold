# Architecture

## USB ownership

The physical stack deliberately separates transport by device state:

- `045E:02B0` Motor → Microsoft `winusb.sys` → Broker.
- `045E:02AE` Camera → Microsoft `winusb.sys` → CameraBridge.
- `045E:02AD` NUI Audio boot → Microsoft `winusb.sys` → AudioBridge bootloader uploader.
- `045E:02BB&MI_02` / `045E:02C3&MI_02` NUI Audio runtime → Microsoft inbox USB Audio class driver → WASAPI → AudioBridge.
- `045E:02BB&MI_00` / `045E:02C3&MI_00` 1473 control runtime → existing Microsoft WinUSB or Remold fallback → Broker.

For model 1473, setup applies port-scoped identity to camera bcdDevice 02.05 and preserves `02C2` on the Microsoft hub stack. The `02AE` camera, `02BB/02C3&MI_00` control function and `02BB/02C3&MI_02` USB Audio function are configured independently: a control-protocol failure never blocks camera or audio installation.

Model 1473 is a distinct physical backend behind the same public control contract as model 1414. Its `02AE` camera keeps the same product ID as the 1414 camera but reports a different USB bcdDevice value; CameraBridge keeps the same per-device discovery/pipe architecture. LED, tilt and accelerometer commands use the alternate bulk protocol on `02BB/02C3&MI_00` (`OUT 0x01`, `IN 0x81`), while `MI_02` remains owned by Microsoft USB Audio/WASAPI. A fresh 1473 MI_00 session performs the required post-firmware LED prime once; it is controller initialization, not UI decoration. LED/status transactions retain bounded recovery, but Tilt is one-shot: a successful `0x803B` OUT transfer is never automatically repeated because a later ACK/status sample is delayed. The Broker resolves the model from the `02AE` camera hardware ID (`REV_010B` is 1414) before choosing `02B0` or `MI_00`, serves every control connection on its own thread and answers `Status` with `ERROR_BUSY` while a Tilt is travelling. CameraBridge is the only periodic status owner: it polls 1414 every 25 ms and 1473 every 500 ms only while a ScannerPort client or a leased frame consumer (virtual camera, IP camera viewer) is active, and attaches the latest sample younger than 250 ms (1414) or 1500 ms (1473) to every ScannerPort frame and shared-memory RGB frame. The motion contract is documented in [`docs/MOTION.md`](../MOTION.md).

The audio path is therefore:

`02AD boot/WinUSB → Microsoft UACFirmware 01.02.709.00 upload → 02BB/02C3 MI_02/USB Audio → WASAPI → per-Kinect multi-client raw 4-channel bus Kinect360RemoldAudio-<device-id> → independent SynKinect Studio DSP instances (Microphones + Acoustic Scanner)`

No Remold USB/audio kernel binary is required. The virtual camera remains a Media Foundation user-mode component.

## UAC firmware transition

The build downloads the Microsoft Kinect for Windows Runtime v1.8 installer, verifies its SHA-256, extracts UACFirmware 01.02.709.00 without installing the Runtime, and embeds it into AudioBridge. The same image is used for models 1414 and 1473. AudioBridge uploads the raw UAC image at `0x00080000` through boot bulk endpoints `0x01/0x81` and launches entry point `0x00080030`. The `02AD` boot function then disconnects and the UAC runtime is discovered in the Microsoft 1.8 `045E:02BB/02C3` family.

Runtime USB-audio scheduling belongs to the inbox USB Audio driver; AudioBridge works at the Windows audio endpoint boundary and never captures microphone ISO traffic through the Remold WinUSB control path.

## WASAPI capture boundary

AudioBridge tracks physical Kinect presence independently from WASAPI readiness. A stable per-device audio node is created as soon as any transport for that physical Kinect is present (camera, 1414 motor, 02AD audio boot, 1473 runtime control, or the UAC capture function). MMDevice/WASAPI binding then resolves the corresponding `02BB/02C3&MI_02` endpoint by PnP parent/container identity, with only unambiguous fallbacks. This gives models 1414 and 1473 the same reconnect behavior while Windows is still re-enumerating USB Audio. Compatible shared-mode PCM16/24/32 or float32 formats are converted to the Remold S32LE ABI.

The public microphone format remains 4 channels, 16 kHz, 32-bit signed little-endian PCM, 256 samples/channel. Endpoint identity is per Kinect: `\\.\pipe\Kinect360RemoldAudio-<device-id>`, with `\\.\pipe\Kinect360RemoldAudioControl-<device-id>` for that Kinect's volume/mute control. The control endpoint belongs to the physical Kinect node and remains addressable independently of the instantaneous WASAPI capture state; the raw-audio stream may reconnect without disabling mixer control. If the UAC endpoint is not ready yet, Studio reports reconnecting rather than silently omitting that model's audio identity.

## Camera frame fan-out and native IP runtime

`Kinect360RemoldCameraBridge.exe` is the only user-mode owner of the physical camera WinUSB interface. ScannerPort receives sensor-native camera payloads directly. Separately, baseline RGB is converted to NV12 only for the RGB-only `Global\Kinect360RemoldFrame-<device-id>` operating-system fan-out. Each mapping belongs to one physical Kinect and carries no Depth region. IP camera and Media Foundation virtual camera are read-only consumers; neither can request a physical sensor mode change. Every RGB slot carries the frame's motion sample, and consumers renew `Global\Kinect360RemoldFrameLease-<device-id>` (the only writable field) while they use frames. CameraBridge runs the `0x81` video engine and samples motion only while a ScannerPort video subscription or a renewed lease exists, exactly like the Linux camera service.


The camera bridge enumerates every installed Kinect camera interface. Each interface receives a stable hashed device ID derived primarily from its Windows USB physical location path (with device instance/path fallback), a private named pipe `\\.\pipe\Kinect360RemoldScanner-<device-id>`, and an entry in `%ProgramData%\Kinect360Remold\devices.tsv`. Control readiness is established with a device-scoped Broker `Ping`: it opens/resolves the exact physical 1414/1473 control backend and publishes the control pipe only when the reply reports `PhysicalMotor`, without polling accelerometer/status just to keep the UI enabled. This avoids treating the model-1473 camera placeholder serial `0000000000000000` as a unique identity. Hot-plug reconciliation is incremental, so a path change on one sensor does not stop every other camera worker. Named-pipe transport is multi-client for stream sets allowed by the single-video-engine hardware mask. RGB HQ is a persistent driver setting stored per `device-id`; Studio system controls and `KINECT` modify that setting, the active Scanner session renegotiates immediately after a confirmed change, and the matching virtual camera lists the 1280x1024 HQ media types first (as its default) for newly opened clients, while an already streaming client keeps its format and receives scaled frames. Surveillance owns exactly RGB or IR and never subscribes Depth; when it leaves the foreground it releases IR so other color consumers can resume without a persistent endpoint conflict. Every Ready camera publishes its own stable RGB mapping. CameraBridge reconciles one Media Foundation virtual camera named `Kinect Xbox 360 Camera [device-id]` for each Kinect and preserves that logical instance during the reconnect grace window. No Kinect is promoted to a global primary camera.

The Media Foundation source DLL is deployed under Program Files with a SHA-256-derived filename and is registered as the active COM source before CameraBridge starts. The file is immutable for that build. This allows an installer update to succeed even when Windows Camera Frame Server still has a previous source DLL mapped. After registering the new source the installer stops the demand-start Frame Server services (never force-killing their shared svchost), so the next camera open always loads the source that matches the installed CameraBridge. CameraBridge reads the active COM path rather than assuming a fixed runtime DLL filename.

Physical camera state is device-owned rather than module-owned. ScannerPort clients only express desired streams; the bridge arbitrates endpoint `0x81` modes and gives projector/depth ownership to the Depth supervisor. ScannerPort receives sensor-native RGB Bayer, packed IR10 and packed Depth11; SynKinect Studio performs demosaic, IR unpack/crop and calibrated raw→millimetre conversion in user-space. The WinUSB isoch buffer for `0x81` remains registered across normal RGB/IR/HQ module handoffs; the bridge stops firmware capture, cancels/requeues reads on the same buffer and restarts the selected mode without a normal pipe reset. The same stop/requeue path idles the video engine when the last video consumer leaves. After the first Depth request, endpoint `0x82` likewise remains registered until the physical camera session ends, while register `0x06` is merely toggled according to active Depth/IR demand. A video-engine fault terminates only the affected device's current WinUSB camera session; a genuine depth fault rebuilds only `0x82` from a defined OFF state. Scanner, Interactivity, Surveillance, virtual camera and external ScannerPort clients all use this same per-device runtime.

The IP service is optional and remains disabled after installation. If the user later enables it, the service selects or is pinned to one Ready Kinect from the capability manifest, reads only that Kinect's RGB-only NV12 shared mapping, performs NV12-to-BGR conversion and Windows Imaging Component JPEG encoding, then serves authenticated HTTP/MJPEG with Winsock. It never calls WinUSB and never connects to a per-device `Kinect360RemoldScanner-<device-id>` endpoint, so enabling network viewing cannot steal a scanner session or reconfigure RGB/IR mode. Deployment defaults, firewall scope, port, frame rate and JPEG quality are centralized in `build/Product.psd1`; LAN exposure remains a separate explicit administrator action and the service runs as LocalService rather than LocalSystem.
